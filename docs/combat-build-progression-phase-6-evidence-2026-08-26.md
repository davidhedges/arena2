## 3. Editor behavior and authority

`HubCombatBuildEditorModel` clones the current canonical build into a mutable
presentation draft. It preserves all discipline configurations, including
dormant ones, while counts include selected configurations only. Removing a
discipline therefore hides it from the active build without discarding its
weapon, colors, schools, exact slots, or passives; adding it again restores
that configuration. A never-configured discipline receives the server-projected
legal starter weapon.

Active assignment replaces the requested exact action slot. Passive selection
uses the DTO's stable list ordering; clicking any visible empty passive cell
appends consistently because the contract has no passive slot identifier.
Ability uniqueness is preserved across selected and dormant configurations.

Staff ability choices are filtered by the Staff card's selected schools.
Removing a school with assigned abilities is held until those abilities are
cleared so the user can submit the required atomic change. No school creates a
discipline card, weapon, or independent action bar.

The screen reads every limit and slot from
`HubCombatBuildContractSnapshot`. Neither the screen nor editor model owns the
20/16/1..3 constants or a validator. Save calls only:

```text
HubNetworkManager.SaveCombatBuild(HubCombatBuildEditorModel.ToDraft())
```

The reducer remains authoritative. Failed reducer text is retained verbatim,
including its stable `COMBAT_BUILD_*` code; the client owns no parallel error
map.

## 5. Behavior tests

`CombatBuildEditorUiTests` adds four focused tests:

1. add/remove and dormant configuration restoration, selected-only counts,
   exact active-slot replacement, passive ordering, and atomic draft shape;
2. canonical card/school/bar/picker layout with no primary/secondary or stat
   allocation controls;
3. behavioral round-trip of every stable server `COMBAT_BUILD_*` code through
   the UI rejection presenter, plus proof that no client code map exists; and
4. canonical Hub projection consumption with no legacy display-table query.

The tests compiled into `Arena.EditModeTests.dll` and were invoked directly
through Unity's bundled Mono runtime against the compiled
`Assembly-CSharp.dll`:

```text
PASS EditorModel_RestoresDormantConfigurationAndPreservesExactAssignments
PASS EditorLayout_ExposesCanonicalCardsSchoolsBarsAndPicker
PASS EditorDisplaysServerValidationCodesVerbatimWithoutOwningACodeMap
PASS HubProjectionUsesCanonicalCombatBuildMetadata
```

The repository rule did not authorize Unity batch mode. A command launched
without the `-batchmode` flag but with Unity's `-runTests` option unexpectedly
switched the Editor internally into batch mode, emitted no test-result file,
and exited. That attempt is invalid evidence, was not retried, and is not
counted as a test pass. The focused tests above were therefore executed without
launching Unity, and the ordinary compile/import evidence below is reported
separately.
